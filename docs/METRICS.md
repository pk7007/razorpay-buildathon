# Metrics — AI Finance Controller

Every number here is regenerated by one command. Nothing is hand-edited.

```bash
python scripts/run_reconciliation.py --evaluate     # accuracy, dev vs held-out
python scripts/run_reconciliation.py --benchmark    # throughput
```

They are also served live by the running service at `GET /api/evaluation` and
`GET /api/benchmark`, so a reader can check this file against the code.

## Why there is a held-out split at all

The matching rules in `reconcile.py` were developed while looking at the three
bundled datasets, all generated from **seed 7**. Scoring the matcher on those
same datasets measures how well the rules were *fitted*, not whether they
generalise — the solver and the exam were written by the same person.

So the datasets are split the way an ML benchmark is:

| | seeds | role |
| --- | --- | --- |
| **dev** | 7 | what the rules were written against. Reportable, but not evidence. |
| **held-out** | 101–105 | never looked at while writing a rule. **These are the numbers that count.** |

`evaluate.py` implements the split; `tests/test_evaluate.py` asserts the
thresholds so a regression fails CI rather than quietly degrading the claim.

## Definitions

| Metric | Definition |
| --- | --- |
| **Auto-match rate** | entries placed in a match group / total entries |
| **Precision** | correctly-matched entry *pairs* / all predicted pairs |
| **Recall** | correctly-matched pairs / all true pairs in the answer key |
| **Exception-category accuracy** | exceptions whose category equals `truth.json` / labelled exceptions |
| **₹ in wrong groups** | rupee value sitting inside an incorrect group — the cost of a false match |
| **Generalisation gap** | dev metric − held-out metric. Large ⇒ the rules were fitted, not learned. |
| **Replay stable** | a second run produces an identical groups+exceptions fingerprint |

Precision and recall are computed on **pairs** (both entries in the same group),
not whole groups, so one giant group cannot inflate the score.

## Accuracy — offline heuristic resolver (no LLM key)

| | runs | entries | precision | worst run | recall | F1 | exc-category | ₹ in wrong groups |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| dev (rules tuned here) | 3 | 943 | 1.0000 | 1.0000 | 1.0000 | 1.0000 | 1.000 | ₹0 |
| **held-out (unseen seeds)** | **15** | **4,631** | **1.0000** | **1.0000** | **0.9928** | **0.9962** | **0.968** | **₹0** |

- **Generalisation gap: F1 0.38 pts, recall 0.72 pts.**
- All 15 held-out runs replay-stable.
- **1 of 15 runs imperfect:** `messy` seed 102, precision 1.0000, recall 0.8927.

### Why precision is the metric held hardest

A wrong auto-match silently closes the book on real money. An exception costs a
human two minutes. The asymmetry is deliberate everywhere in the engine: when a
rule cannot decide, it declines. That is why **₹0 landed in an incorrect group
across 4,631 held-out entries**, and why recall — not precision — is where the
one imperfect run shows up.

### The imperfect run, in full

On `messy` seed 102 the engine meets a batch payout where **two different
same-day payment triples sum to exactly ₹2,152.12**. Nothing in the data
distinguishes them: same day, same total, no shared identifier. Constraint
propagation across the day's other settlements does not break the tie either.

The engine refuses to guess. It records an `ambiguous-split@v1` audit entry
naming the competing candidates, marks the affected groups `ambiguous_split`,
and puts their value in its own money bucket rather than reporting it as
unpaid revenue. Recall drops to 0.8927 on that run as a result.

Resolving it needs a join key the batch files do not contain — Razorpay's
settlement recon report, which maps payment → settlement directly. That is
listed under future work, not papered over.

## Throughput

| records | seconds | records/sec | auto-match |
| --- | --- | --- | --- |
| 1,126 | 0.08 | 13,527 | 98.1% |
| 5,840 | 0.52 | 11,194 | 98.2% |
| 23,565 | 2.22 | 10,622 | 98.2% |
| 58,908 | 6.56 | 8,976 | 98.2% |

Single process, no database, otherwise-idle machine. Across a **50× range
throughput degrades 1.5×** — effectively linear. Accuracy is flat across the
range, so the scaling is not bought by matching less.

Getting here took removing three O(n²)s found by profiling, all documented in
the git history: an edge-index scanned per group, `list.remove()` on pydantic
models inside a fixpoint loop, and a per-exception scan over every ledger row.

## What each benchmark contains

`synth.py` injects these with a ground-truth label for each:

| Scenario | clean | realistic | messy | expected outcome |
| --- | --- | --- | --- | --- |
| clean 4-way flow (fee + 18% GST, T+2) | ~5/day | ~7/day | ~6/day | one `complete` group |
| split batch (3–5 payments → 1 payout) | 1 | 3 | 5 | one group via `split-settlement` |
| merged payout (2 settlements → 1 credit) | 0 | 2 | 4 | one group via `merged-bank-credit` |
| double-booked ledger entry | 0 | 2 | 5 | `duplicate` exception |
| revenue captured, payout never landed | 0 | 2 | 5 | `payout_overdue` → recoverable |
| bank credit never booked | 0 | 2 | 5 | `missing_in_ledger` exception |
| payout raised, credit after the window | 1 | 2 | 4 | `awaiting_payout` group |
| bank deducted an extra charge | 0 | 2 | 4 | `fee_mismatch` exception (settlement named) |
| off-gateway transfer, no shared id | 0 | 2 | 3 | paired by the **residual resolver** |

The last row exists specifically so the resolver has work only it can do:
deterministic rules cannot pair a bank credit to a ledger entry that shares no
identifier. Resolver share on the anomaly datasets is ~2%.

## Honesty notes

- These are the **heuristic** resolver's numbers — the weaker backend. They are a
  floor, not a best case. With `ANTHROPIC_API_KEY` set the LLM handles the
  residual tail instead; `resolver_mode`, token counts and USD cost are reported
  on every run.
- **The LLM path is verified live but contributed no measurable accuracy.**
  `scripts/verify_llm.py` passes against the real API ($0.0068, one call), and
  on that input the model matched the deterministic scorer exactly; see
  [`LLM.md`](LLM.md). Every number in this document was produced with it
  switched off. Its contract is covered by mocked tests
  (valid proposals accepted, hallucinated ids rejected, low confidence rejected,
  arithmetic-implausible groups rejected, every failure mode falling back to the
  heuristic), and the live path is verified by `scripts/verify_llm.py`. What is
  not measured is whether the model *beats* the heuristic on a hard residual --
  on the one verified call it matched it exactly.
- The benchmark is **synthetic**, which is what Track 4 asks for. It models the
  fee/GST/T+2 structure and nine real reconciliation failure modes, but it is not
  a substitute for a merchant's actual month.
- **FX-adjusted international settlements are not modelled.** They need the
  settlement recon report as a join key.
- Throughput was measured on one developer machine, single process. It is a
  relative scaling claim, not a capacity guarantee.
